# Decision log

Key design decisions, so the reasoning isn't lost.

| Date | Decision | Why |
|---|---|---|
| 2026-09 | Classification rules live in a spreadsheet (the crosswalk), not in code | The maintainer can change categories without programming |
| 2026-09 | Most specific crosswalk row wins; unlisted modifiers flatten to the plain row | Keeps the sheet small while allowing detail where it matters |
| 2026-09 | Household dumping sizes (small, medium, large) are separate layers | Small items and large loads are different problems, so they need separate counts |
| 2026-09 | A permanent `UNCLASS` row catches dumping photos without a size | Nothing is silently lost; it works whatever code OLM uses for "not sure" |
| 2026-09 | Column `include on map` is the only on/off switch; "local key = OLM key" is a consistency check | Two competing rules would contradict each other |
| 2026-09 | Audit counts for "not used" and "unmapped" | Data problems become visible numbers instead of silent gaps |
| 2026-09 | Liquor packaging reclassified: boxes to `food/box`, whole items to `food/packaging`, pieces by material | Cannabis packaging moved to smoking + `THC`; the alcohol key was inconsistent |
| 2026-09 | The "low occurrence" group is retired; rare items join their logical parent | Richer data: a bottle cap belongs with drinks, not in a miscellaneous pile |
| 2026-09 | Three-level layer tree: Group → Subgroup → Layer | Some topics (like straws or drinks) need a middle level; others don't |
| 2026-09 | Map counts are items, not photos | One photo can hold many items; photo counts go in the audit |
| 2026-09-25 | The municipal stream columns (Maple Ridge name, Maple Ridge stream, Vancouver audit category) and "In my sample" were removed from the crosswalk, and `alcohol/packaging` was made an included layer, Liquor Packaging | The crosswalk was reviewed before public release. Stream columns were redundant and confusing at this stage and will be rebuilt one at a time in Stage 4. "In my sample" came from a check made when a paging error had cut the data pull short, and the full data set makes it unnecessary |
| 2026-09-24 | An incomplete or empty fetch fails the sync instead of publishing partial data | A 200-page cap had silently cut the map to 1,600 photos; a failed run leaves the last good data live |
| 2026-09-24 | Page requests retry with increasing waits (2s, 4s, 8s) on network errors, 429, and 5xx | Brief hiccups shouldn't waste a 12-hour run |
| 2026-09-25 | If OLM rejects the login token (HTTP 401) mid-run, log in again and retry the page, up to 3 times per run | A token was rejected at page 173 of 313 and the run had to stop; a fresh login recovers it |
| 2026-09-25 | The workflow runs `git pull --rebase` before pushing its data commit | A push to `main` during a sync made the bot's push fail and lost that run's data |
| 2026-09-25 | Each photo's `groups` list is sorted | A set gave a random order every run, causing large pointless data commits |
| 2026-09-25 | OLM's object type is kept as `object_type` on standard tags, and the crosswalk's "with Secondary Modifier" column matches against it. "Skip / not sure" saves no type and falls to the blank row | Dumping sizes and drink types were being dropped |
| 2026-09-25 | Build order: crosswalk engine and layer tree map, then legacy review and reclass, then GIS map features, then municipal streams | The review is the biggest human effort and the streams depend on a finished tree and conformed data |
| 2026-09-25 | Claude maintains the REVIEW backlog workbook after the maintainer's OLM edits, and the audit reports orphan tags on their own line, separate from unmapped | The backlog is too large to work by hand, and orphan tags are tagging errors fixed in OLM, while unmapped means a gap in the crosswalk |
| 2026-09-25 | Legacy tag review is done per tagged object, and retired, excluded, and orphan tags are reclassed in OLM | Counts are items, not photos, and fixes happen at the source |
| 2026-09-25 | Work happens directly on `main`: local copy, local test, then push. No feature branches, staging site, or preview deploys | Branches are confusing to track for a solo beginner, and a display error on the public map carries no data risk. Free GitHub Pages sites are always public, so a private test site is not possible at $0 |
| 2026-09-26 | Foil pieces (`food/tinfoil`) move from Household to the Piece group as Foil Piece. A new layer, E-waste Piece (`other/other` + custom tag `E-waste`), is added under Household. The `food/other` layer becomes "Organic Debris, Misc." | Foil is found as fragments from many sources, like the other Piece layers. E-waste needed its own count |
| 2026-09-26 | The crosswalk's Notes are written for publication, and the Google Sheet is the source of truth for them. After an edit the whole sheet is re-exported, and git stores `crosswalk.csv` with LF line endings (`.gitattributes`) | The repo is public. Notes tidied only in the repo copy were overwritten by the next export. Sheets exports CRLF, which made every line look changed |
| 2026-09-26 | A crosswalk change reaches the map by exporting to `config/crosswalk.csv` and pushing. The workflow also runs when that file changes | Git keeps every version of the crosswalk, and the map updates without waiting up to 12 hours. Reading the Google Sheet live would skip that record and add an outside point of failure |
| 2026-09-26 | The map shows one dot per layer per photo, nudged slightly apart when a photo has several layers | Each dot can take its layer's colour, and layer checkboxes filter cleanly. One dot per photo would hide the other litter in it |
| 2026-09-26 | Map colours are assigned by code: a colour family per Group, a shift per Subgroup, and shades per layer | New layers added in the sheet get a colour with no extra work. Too many layers share some groups for colour alone to tell them apart, so the checkboxes and popups name each layer |
| 2026-09-26 | REVIEW objects are shown normally on the map | The audit and the review workbook track the backlog, and hiding about 1,400 objects would leave the map badly incomplete |
| 2026-09-26 | Objects left in place (`picked_up` = false) show as hollow rings; picked-up objects as filled dots. `picked_up` is kept per object as true, false, or unknown | Picked-up status is core data for the project (dog waste is deliberately left in place), and it should be visible without clicking |
| 2026-09-26 | The map has a From/To date filter on local (America/Vancouver) days. A full time slider stays in Stage 3 | OLM stores UTC, so about half the photos (evening collections) would otherwise fall on the next day. A simple range is enough to check a collection day now |
| 2026-09-26 | Dots are shown at OLM's recorded location and are never moved or snapped. Phone GPS accuracy (about 5 to 15 m) is explained in the README instead | The data should match OLM exactly. A display cluster keeps one photo's dots apart by a few pixels without changing the location |
| 2026-09-26 | Group colours use a fixed, colour-blind-tested categorical order, never cycled; colour only hints at the group, and the checkboxes and popups identify each layer | On a map any two colours can meet, and only about three categorical colours stay distinguishable for colour-blind viewers under those conditions |
| 2026-09-26 | The audit report has no timestamp | The workflow commits only when a file changes; a timestamp would create a pointless commit every run |
| 2026-09-26 | A heatmap view was built and published ahead of the legacy review, by the maintainer's choice; the rest of Stage 3 keeps its place after the review | It was quick to add with MapLibre's built-in heatmap, needed no data change, and is useful now |
| 2026-09-26 | The heatmap is weighted by items, uses one warm hue from pale to deep red, fades into the dots at street level, and carries a note that heat is relative and reflects collecting effort | Items match the map's counting rule; amount calls for a single-hue sequential scale, never a rainbow; clickable dots stay available; citizen-science heat mostly shows where collecting happened |
| 2026-09-26 | "Left in place only" filters both views rather than being a heatmap-only option | One control with one meaning is easier to follow, and it also isolates the rings in the dots view |
| 2026-09-26 | The GeoJSON carries the layer tree order as `mrolm_layers` | The map needs the sheet's group order and the data can't infer it; the list comes from the same run as the data, so the two always agree |
| 2026-09-25 | Audit control and reporting rank above deployment safety. Data-shape changes are additive, or the workflow is run right after the push | The value of the project is data that can be confirmed clean. The map can lag the data by up to 12 hours, so old and new shapes must both work in the meantime |
| 2026-09-27 | Proof of concept declared achieved; criteria 5 (legacy data conformed) and 8 (newcomer read-through) became ongoing refinements | The goal was to show OLM's global schema can be translated into local terms, with the crosswalk as the tool that manages the local schema, and both work on the live map. The two moved items improve data quality and docs but don't test the idea |
| 2026-09-27 | Code under MIT; data under ODbL 1.0 with "© OpenLitterMap & Contributors" credited on the map | OpenLitterMap's data is ODbL, and the ODbL's share-alike rule means a database built from it must stay ODbL. MIT is the simplest open code license, and no OpenLitterMap code (GPL v3) is copied |
| 2026-09-28 | Pieces are tracked as their own objects by material, not linked to a parent item | Pieces are the majority of MROLM's object counts, so they're measured directly. Matching pieces to parents needs finer visual analysis than the project does, and the photos keep that option open |
| 2026-09-28 | `smoking/lighters` (Butane Lighter) is for whole lighters only; lighter pieces go to a material piece key, E-waste, or `other/other` | Follows the pieces-by-material decision, so Butane Lighter counts whole lighters and a piece is counted with pieces of its kind |
| 2026-09-28 | The custom tag `Piece` is no longer used for tracking; pieces are identified by their key and the crosswalk's MROLM layer | The crosswalk never matched on `Piece`, so it added tagging work without changing any count |
| 2026-10-02 | The review workbook has a `Reviewed` date column, separate from Status. An object counts as reviewed if it has an edit or note, or its photo was uploaded before the pass date | Status comes from the crosswalk (REVIEW means the key carries a fix note), so it can't show whether a person checked an object. The maintainer reviewed every photo in OLM on 2026-10-02 and only marked the ones needing changes, so "no edit" has to count as reviewed |
| 2026-10-02 | Photos showing addresses, licence plates or other personal information, and not-picked-up litter that didn't follow protocol, are deleted in OLM rather than hidden in the map code | The photo link is published on the map, and tagging problems are fixed in OLM itself, not patched in code |
| 2026-10-02 | The legacy review is declared complete: Not used (RECLASS), UNCLASS, orphan tags and UNMAPPED are all 0 | Every photo was reviewed, 166 were retagged in OLM and verified against the dry-run plan, and the workbook shows all objects reviewed. REVIEW stays high by design, because it marks keys whose crosswalk row carries a fix note |
| 2026-10-02 | Stage 3 zone summaries use the City of Maple Ridge's neighbourhoods, from the Planning Department's neighbourhoods map (5 March 2025), cited as published. The municipal stream (Stage 4) now happens only if COMR publishes or uses litter categories and takes part. The City of Vancouver stream is dropped | Neighbourhood totals express the data in municipal geography with no City programme needed. A stream in municipal categories only means something if it follows the City's own scheme, and MROLM's groups are a volunteer's logic. The map shows Maple Ridge, so another city's categories would confuse readers. Source notes: `docs/maple-ridge-community-areas.md` |
| 2026-10-02 | Zones are rectangles placed where photos are, named `<neighbourhood>_zone_<letter>`, and each belongs to one neighbourhood by majority of its photos. Zone edges sit in the quietest spot within 60 m of each cross street. Each card reports photos within an assumed 15 m GPS error of an edge. No per-photo GPS correction | OLM sends no GPS accuracy, so correcting a photo would invent an error. With edges on the cross streets 24% of photos were within 15 m of an edge; at the quiet spots it is 2.9%. The data runs along 240 St, which is also a neighbourhood line, so cutting zones down the road would split most photos by drift. Details: `docs/zones-method.md` |
| 2026-10-02 | Only neighbourhoods with photos get zones, and every photo gets one, however few a zone holds. A neighbourhood is added by two rows of config, not code | One volunteer's run is a live model, so a thin area is shown as thin (with collection days on its card) rather than hidden. Today that is Cottonwood only: no photo is far enough east of 240 St to belong to East Maple Ridge or Albion |
| 2026-10-02 | Neighbourhoods get one colour each, and zones use that same flat colour. Zones are lettered north to south, so A is the top zone. The panel's colour key is a checkbox tree like the litter layers: a neighbourhood and its zones, where ticking the neighbourhood ticks its zones. A ticked area is drawn on the map and has a filled swatch with its letter; an unticked one is not drawn and has an empty swatch that still shows the letter. The neighbourhood shape is drawn while any of its zones is ticked. Zoom (14, a first guess) chooses whether neighbourhoods or zones are drawn. The letter or name label (at the area's centre) and one card appear only while an area is hovered or selected, on the map or in the key. The card sits in the free space beside the zones, and the neighbourhood card ranks its zones by items found. Labels are HTML markers | A progressive gradient or alternating tints did not tell zones apart and read as "more litter". Letters match the order a viewer reads down the map and the key. Ticking works like the layer tree, so it needs no new idea to learn. Labels and cards shown only on demand keep the map clear, and beside the zones the card covers nothing. Markers avoid depending on the basemap's fonts, and their positioning must never be overridden in CSS (an override once stretched and displaced them). The ticks hide an area's overlay only; they do not filter the dots |
| 2026-10-02 | A litter density score per zone (items found per full-coverage visit, with a radial gauge) was considered and dropped | A fair density needs the zones, the dataset and the collection schedule coordinated, and effort per visit is not measured. Visits covered 18% to 94% of a zone's length by median, so counting every day would mislead, and counting only full visits left some zones without enough visits. MROLM shows plain counts and says on the card that they show where collecting happened. A density measure would need planned, repeated coverage of fixed blocks |
| 2026-10-02 | Dates are one set of selected collection days. A list of the days, month chips, weekday and weekend chips, and the presets all add or remove days from it, and From/To set it to the days in a range. Any other change clears the From/To boxes so they never disagree with the selection. "Last 7 days" and "Last 30 days" count back from the latest collection day, not from today. Chips tick like boxes, so months can be mixed. Time of day and a side-by-side compare are left out for now | Photos come in on 20 collection days with big gaps between them, and a day is one run (1 of 20 days had a 2-hour gap), so a calendar range alone is awkward and the days themselves are the natural unit. One set means every control works with every other. Counting back from today would give an empty map once the data is a few weeks old. Counts beside each day follow the layer ticks and "Left in place only" but not the day selection, so you can see what ticking a day would add |
| 2026-10-02 | The panel is folding sections: Litter layers (open), Dates (folded) and Map areas (folded), with "Left in place only" above them beside the picked-up key. A folded section keeps a status on its summary line ("5 of 20 days" or "5 of 6 zones", bold when it is filtering the map), and Map areas carries a swatch and a one-line explanation. Areas get a pointer cursor | At laptop height the layer tree, the main control, was below the fold behind two filter groups, and a first-time visitor could not tell what the shaded areas were. Folding keeps filters one click away while the status shows when one is active, so a folded filter never works unseen. The one-liner is visible without opening anything |
